# Submodule Disk-Saving Workflow

## Trigger Examples

- "This repository has many submodules; can setup use less disk?"
- "Can we hard link or reflink submodules across worktrees?"
- "This checkout is a linked worktree of a large repo. Can submodules reuse the main checkout?"
- "After using submodule linked worktrees, should I still run `git submodule update --init --recursive --depth 1`?"

## Approach Comparison

### Limit The Active Set

Use explicit submodule paths or `submodule.active` when the build does not need every submodule.

```bash
git submodule update --init --recursive --depth 1 -- third_party/libalpha third_party/libbeta
```

This is the simplest and safest disk saver because unused working trees and object stores are never created.

### Use Alternates With `--reference`

Use this when the target checkout should keep ordinary submodule ownership but reuse objects from an existing clone.

```bash
git submodule update --init --recursive \
  --reference /path/to/source/.git/modules/third_party/libexample \
  -- third_party/libexample
```

Notes:

- `git submodule update --reference` takes a reference repository, not a superproject-to-all-submodules mapping.
- For repos with many different submodule URLs, run per path with the matching source repo.
- Do not use `--dissociate` when disk savings matter.
- Alternates break if the referenced object store is removed or pruned past required objects.

### Use Linked Worktrees For Submodules

Use this when the source checkout already has `.git/modules/<submodule-name>` and the target is another worktree that should share those object stores.

Select exact top-level submodule paths before running the helper. An empty path list is rejected rather than expanded to every submodule. Use `--all` only when the task explicitly authorizes the complete top-level set.

For an apply invocation, the helper securely binds the top-level `.gitmodules`, the primary and any shared superproject index file objects/bytes, and the selected stage-0 gitlink rows before preflighting every selected target, including recursive descendants. The shared-index query deliberately preserves existing split-index state; applying the ordinary `core.splitIndex=false` write-suppression override to `rev-parse --shared-index-path` would hide the `link`-named file that the receipt must bind. Each selected-gitlink `ls-files` query runs with an absolute `GIT_INDEX_FILE` naming a short-lived owner-private mode-`0400` copy of the already bound primary bytes. When the primary carries split-index `link` state, the same exact view contains the bound shared bytes under their original `sharedindex.<hash>` sibling name. Descriptor-bound digest leases and an exact directory inventory enter the child exec gate, and explicit verified cleanup removes the view afterward. Thus the protected selected-row property is derived from the captured primary/shared bytes rather than a second open of the live index pathname; a same-inode, same-size valid-index ABA restored before the surrounding receipt checks cannot select an attacker gitlink. Managed tracked-status and `read-tree --dry-run` probes can invoke content conversion, so each probe runs against a separate short-lived owner-private common-gitdir view copied from the already bound source config and common `info/attributes` content or absence. That view also contains a mode-`0400` copy of the already captured managed index, selected with an absolute `GIT_INDEX_FILE`; Git therefore does not consult the live admin index during either probe. The view materializes exactly the current-HEAD and target checkout object closures into one private no-delta pack and does not expose the live source object directory. The canonical v2 pack index must enumerate exactly that OID union, and `verify-pack` plus the normal streaming closure verifier recheck the private pack. Exact inventories bind every entry in the private common-gitdir, `info`, `objects`, `objects/info`, `objects/pack`, and `refs` directories, so alternate/promisor/lazy-fetch, loose-object, bitmap, reverse-index, commit-graph, multi-pack-index, shallow, ref, and extra-pack inputs remain unavailable. Every source/private directory identity, exact inventory, control-file byte receipt, private-index receipt, pack-index byte receipt, pack descriptor/digest, and source-absence receipt is revalidated by the child immediately before exec. The receipt is revalidated before each authorized fetch and immediately before the first worktree mutation. A path replacement, byte-content change, access-policy change, shared-index path-set change, selected-row drift, or launch-window filter/object insertion blocks the plan; an mtime-only transition does not. A failure in that phase prevents the apply phase from starting. `--dry-run` stops after the isolated plan/preflight. When the task already names the exact paths and the preflight succeeds, the apply phase does not need a separate confirmation solely because the plan was printed.

For every existing managed worktree, the preflight first opens and retains the target directory, managed control chain, detached HEAD, and raw admin index before any tracked `git status` or `read-tree` command exists. It verifies the captured index checksum and exact stage-0 semantics against HEAD, rejects split-index plus hidden or unknown extensions, and derives a semantic digest that deliberately excludes stat-cache metadata. Both probes use the held target directory as `cwd`, explicit `--git-dir=<bound-admin> --work-tree=.`, and the private captured index. A same-inode exact-byte ABA against the live index—including a temporary `assume-valid` rewrite restored before terminal validation—is therefore harmless to the probe result because Git never reads those live bytes. The helper still retains the raw live index descriptor and revalidates its exact identity, content, effective access, control endpoints, and HEAD after every probe; persistent replacement, content drift, unreadable state, or access-policy drift fails closed. It derives the bounded `HEAD..target` write set with renames disabled and binds the identity and access policy of each existing object and parent needed by that write set. It checks only write-relevant ignored prefixes and descendants rather than enumerating unrelated untracked content. Final revalidation repeats the descriptor-bound raw-index proof before the actual checkout, which uses `--no-overwrite-ignore --no-recurse-submodules`. The selected preflight property is supported raw-index semantics; stat-cache churn alone is not treated as a checkout mutation, and working-tree content is assessed separately by status against the immutable private index.

Every planned source also has a completeness receipt. The helper binds the direct source gitdir and content-binds its config, rejects `commondir` indirection, include, promisor/partial-clone, `.promisor` pack-marker, and alternate-object policy, and revalidates the absence of `commondir`, `objects/info/alternates`, and `objects/info/http-alternates`. Under a held no-follow descriptor for `objects/`, it scans the fixed lower-case `00` through `ff` namespace twice. Each present name is opened descriptor-relatively with `O_NOFOLLOW|O_DIRECTORY`, then its pre-open name, opened descriptor, and post-open name must agree. The receipt separately binds directory-object identity (`dev`, `ino`, type) and POSIX access policy (`uid`, `gid`, mode plus effective read/search access); a symlink, non-directory, later publication, name-to-descriptor race, replacement, or policy drift fails even when the selected commit already resolves through stock Git. Children within the same fanout directory may change without changing those properties. Object content is protected separately: the helper walks the selected commit's complete checkout tree and uses bounded streaming `cat-file --batch` to read every unique commit/tree/blob payload with lazy fetching disabled and independently recompute its SHA-1 or SHA-256 object id. The receipt binds the unique-object count, aggregate logical bytes, and a SHA-256 digest of the sorted object/type/size inventory. A commit-only or object-header-only result is never sufficient checkout evidence.

Before any tracked-status query or target-tree materialization, the helper enumerates every stage-0 regular-file index path plus current and target blobs with non-converting plumbing. It evaluates index attributes with `check-attr --cached`, tree attributes with `check-attr --source=<sha>`, and local `filter.*.clean` / `filter.*.process` configuration. Any selected driver—including one present only in staged-new index content, `lfs`, a required driver, or a non-required driver—is blocked. The later tracked-only status query pins `GIT_ATTR_SOURCE` to the already-inspected current commit; checkout pins it to the inspected target. The helper deliberately has no trusted filter allowlist, so neither status nor checkout can execute an unreviewed repository filter.

Before the first repository read, the helper resolves one absolute regular-file Git executable, copies its bounded bytes to an owner-private `0500` snapshot, binds the SHA-256 digest of both files, and requires `>=2.45.0` from the snapshot. Every command first performs complete source/snapshot hashing rather than treating stable metadata as content evidence, then retains no-follow descriptors for the snapshot and its parent into the child. The last child-side pre-exec action sandwiches a complete descriptor hash between exact live-parent, parent-descriptor, dirent, executable-descriptor, size, and effective-access checks. Linux executes the inherited `/proc/self/fd` object when that descriptor path resolves to the retained object, with the fixed command path retained as `argv[0]`; otherwise—including macOS, where `/dev/fd` is not executable—it performs the fixed path exec immediately after that gate. The fallback leaves only the documented non-cooperative same-UID gate-to-kernel-open interval outside the portable guarantee. This gate makes `GIT_NO_LAZY_FETCH=1` part of the supported runtime contract rather than an ignored hint on an old Git. Native Windows is rejected before Git discovery because this helper's path and process contracts are POSIX-only.

The same fixed snapshot supplies its absolute `--exec-path`; the helper binds that source directory and snapshots the exact `git-remote-http`, `git-remote-https`, and `git-upload-pack` bytes into a separate owner-private directory. A receipt-bound transport environment sets `GIT_EXEC_PATH` only to that directory; purely local commands omit it and avoid repeatedly hashing unused helper binaries. Each helper's source and snapshot object identity, owner/group/mode, effective access, size, and full SHA-256 digest are transport-receipt state. No-follow leases for the complete closure survive until the transport child terminates, then the parent repeats the full validation before releasing them. This covers Homebrew/Xcode/runtime-prefix relocation without trusting ambient helper lookup. Stock Git still opens helpers by pathname after the child-side gate, so a malicious same-UID replacement inside the remaining interval is a documented non-guarantee; final validation detects observable drift but cannot undo already executed bytes.

All new Git inventories have hard deadlines and aggregate retained-byte, input-byte, entry-count, path-length, pathspec-batch, and access-binding ceilings. Status excludes untracked enumeration, worktree registry reads have explicit record caps, and ignored-path probes share one deadline and retained-byte budget. Root and recursive `.gitmodules` reads share a separate deadline and retained-content budget; root reads use one nonblocking, no-follow regular-file descriptor with repeated digest/content-stability checks, while recursive blobs are size-checked before bounded `cat-file` reads. Process cleanup uses bounded TERM/KILL grace, bounded pipe drain, and bounded direct-child reap. A complete result proves both direct-child reap and EOF for stdout/stderr inherited anywhere in the original process group; either missing proof is structured `process-group-cleanup-v1` incomplete state, never an unbounded final wait or an optimistic return.

One reentrant signal owner starts outside each complete fetch, checkout, add, apply, and CLI transaction and remains active across nested bounded children. Immediately before `Popen`, the parent blocks `SIGINT`, `SIGTERM`, and `SIGHUP`; it creates the child in a fresh session/process group, captures and registers both pipes, and only then restores the supervisor mask. The child restores default handlers and the supervisor mask immediately before `exec`. At parent-owned checkpoints the first latched signal is forwarded to the original PGID. Cleanup deliberately does not call `poll()` first: if the group leader has exited while a descendant still holds a pipe, retaining the unreaped leader also retains the PID/PGID identity through TERM/KILL. Only after bounded group signalling and pipe drain does the parent reap that child. If another owner already reaped the leader, the helper may drain already tracked streams but must not signal a reusable numeric PGID; an open stream then produces explicit incomplete state.

The same latch remains authoritative after a fetch child exits while the helper verifies object availability, publishes the shallow boundary, validates the complete object closure, and durably clears or retains the source fence. It likewise covers managed checkout final validation and receipt publication. New-worktree recovery increments a delivery-deferral depth before it begins registration/target rollback, so a signal arriving inside rollback is remembered but cannot abort cleanup; after registry, target, admin, and control-receipt recovery reaches a terminal state, the helper resumes delivery and raises the original signal. Receipt publication is the add transaction's commit boundary: a signal before it completes takes the rollback path, while a signal at or after the published checkpoint retains the registered worktree and published plan receipts and reports `completed-checkout-published`. Before handler restoration or self-redelivery, explicit plan/runtime owners close transport receipts, private fetch gitdirs, SSH/Git/helper snapshots, and source-transaction descriptors. Every descriptor-bound temporary root and active source transaction also has a registry entry with a machine-readable recovery identity; terminal-signal cleanup walks any registrations the normal owner did not yet release and attaches failures to `cleanup_errors`. The registry retains critical guards strongly until explicit release; those guards do not depend on destructor timing. The helper does not return or retry while a prior mutating group or an unclosed inherited stream may still exist.

An authorized non-recursive fetch requires one exact transport: the task-selected `.gitmodules` URL must byte-for-byte equal the source repository's sole `remote.origin.url`. Git-compatible scp-style SSH forms are recognized before generic schemes, including username-less `host:path`; the negative `://` boundary keeps ordinary and unknown explicit schemes out of that classification. The helper securely reads and binds the source `config` regular-file object and bytes, parses that captured content with includes disabled, and rejects `include`/`includeIf`, `core.sshCommand`, `core.gitProxy`, `core.alternateRefsCommand`, bundle-URI policy, HTTP proxy/header policy, `url.*` rewrites, credential helpers, protocol overrides, worktree config, custom upload-pack/proxy policy, and similar redirection or executable keys. It also extracts a frozen object-write policy. The supported projection preserves `fetch.fsckObjects`, its `transfer.fsckObjects` fallback, `core.sharedRepository`, `core.fsync`, and directly reproducible `core.fsyncMethod` values after strict validation. A valueless supported fsck boolean or `core.sharedRepository` retains Git's native implicit-`true` meaning; an explicit empty fsck boolean remains `false`, while an explicit empty shared-repository policy normalizes to `umask`. Explicit fsck values are normalized with the bound Git runtime's `--type=bool` semantics, and malformed values fail closed. Git-native persisted shared-repository values are normalized as empty/`0`/`false`/`umask`, `1`/`true`/`group`, and `2`/`all`/`world`/`everybody`; valid `0xxx` octal policies remain exact. Duplicate values, unsupported valueless keys, and policy that cannot be reproduced without additional path, filesystem, or ordering state—such as `fetch.fsck.*`, unpack limits, `core.createObject`, `core.fsyncMethod=batch`, or deprecated `core.fsyncObjectFiles`—fail before fetch. Fetch fsck also lacks quarantine, so preserving it does not prove a failed fetch left the object database clean.

Owner-private executable, fetch-control, and managed-preflight checkout-view roots use the same cleanup primitive. Creation registers each root's exact expected fingerprint, path, and purpose without extending its natural lifetime. The Git runtime explicitly owns its executable/helper roots; each transport receipt owns its private fetch gitdir and optional SSH root; each managed preflight owns its temporary checkout view through the tracked-status and checkout-dry-run probes; and the sync plan explicitly closes every unique long-lived receipt on success, dry-run, ordinary failure, and signal failure. The helper holds exact parent/root descriptors, verifies the root dirent against the bound object/access policy, atomically renames it to a random no-replace cleanup name, and only then walks children relative to no-follow directory descriptors. Directory identity and access policy are checked before and after child removal. A pre-cleanup replacement is left untouched; a replacement that wins the check-to-rename interval is atomically restored when possible. Any missing, unreadable, replaced, policy-drifted, or partially cleaned root is retained with `owner-private-temporary-cleanup-v1`, its authoritative observed location, and the expected fingerprint. Pathname-recursive `rmtree` is not part of this security boundary, and correctness does not depend on object finalization timing.

When the source `shallow` entry is absent, the transport receipt also freezes the process umask, effective owner/group, source-gitdir mode/group, and normalized `core.sharedRepository`. The umask is read in an isolated fork child, so capture does not temporarily change the parent process policy inherited by Git. The helper accepts group ownership only when the parent setgid rule determines it or the parent and effective groups already agree; ambiguous inheritance fails before fetch. It computes the regular-file result for `umask`, `group`, `all`, or exact numeric policy, requires owner read/write access, and revalidates the complete creation policy both before fetch and before source-boundary mutation. Absent-to-present publication creates `shallow.lock` with Git's ordinary `0666` request, applies the frozen final mode, and verifies final owner, group, and mode before the no-replace rename. For an existing shallow boundary, the replacement lock must reproduce the receipt-bound uid, gid, and permission mode before exchange; a shared-repository process that would create a different owner or group fails closed rather than silently changing boundary policy. Extended or default ACL entries are not part of this POSIX mode/ownership receipt; the final effective-access checks and mode verification do not claim to enumerate them.

The helper binds the source shallow file object/bytes or its absence under the bound source gitdir, then creates an owner-private control gitdir containing the source object format, bare-repository settings, frozen object-write policy, and a private copy of any existing shallow boundary. Before the network child can write source objects, it descriptor-creates and durably fsyncs `codex-submodule-fetch.pending` with the expected shallow state and a transaction identity. Fetch uses that control gitdir, the bound source object directory, and the exact URL rather than `origin`; the child therefore cannot reread the live source config after final revalidation. The helper also holds no-follow descriptors for the source object directory and its direct parent, matches the directory to the transport receipt, and binds the complete set of direct writable object children: `pack` plus every lower-case loose-object fanout entry from `00` through `ff`. Each name is bound as absent or as the exact accessible directory object; symlinks and other object types are rejected. Immediately before `exec`, the child compares the live absolute parent path, parent descriptor, object entry/name/descriptor, and the complete pack/fanout inventory. Replacing `objects/`, replacing an existing `pack` or fanout directory, or publishing a symlink at any previously absent name before that gate fails before Git starts, rather than redirecting `GIT_OBJECT_DIRECTORY` writes. After the child exits successfully, the helper allows only newly created real fanout/pack directories, requires every pre-existing directory identity and all non-object source bindings to remain unchanged, captures an exact terminal completeness receipt, and uses that receipt for commit and full-closure reads before clearing the recovery fence. A malicious same-UID replacement in the residual interval after the child gate but before stock Git opens the absolute object, pack, or fanout path is outside this portable prevention guarantee; terminal receipt and full-closure checks fail closed and retain the fetch transaction, but cannot undo an already redirected write.

The same launch transaction separately leases the private control plane. It holds the exact owner-private gitdir and its `objects`, `refs`, and `refs/heads` entries through the child pre-exec gate, while `config`, `HEAD`, and any initial private `shallow` remain opened with no-follow descriptors and immutable bounded content copies. The three file specifications retain independent ceilings of 4 MiB, 64 KiB, and 64 MiB, so a valid large shallow boundary is not accidentally constrained by the config limit. If private `shallow` is absent, the root descriptor carries an explicit absent-entry lease for it; `config.lock`, `HEAD.lock`, and `shallow.lock` are always leased absent. The final child check requires exact `ENOENT` for those names and sandwiches every present file's complete descriptor read between live-entry/open-object identity, owner/group/mode, effective-access, and size checks. Any injected regular file, symlink, or other object at an absent name, private gitdir replacement, control-file replacement, or same-inode content rewrite visible there prevents Git from starting; because the persistent source fence already exists, the failure reports a `source-fetch-transaction-v1` recovery identity. Git-created shallow or lock output is allowed only after exec and is governed by the subsequent fetch/boundary receipt. Timestamps are not part of this protected property. As with the source object paths, stock Git still uses absolute control paths after the gate, so a non-cooperative same-UID mutation in that final residual interval is not claimed to be prevented or completely detected portably; later boundary and full-object checks retain the fence when their selected properties become uncertain, but cannot undo a redirected launch.

On success, the helper opens and revalidates the exact source gitdir once, then performs every source `shallow` / `shallow.lock` lookup, open, rename, and cleanup relative to that held no-follow directory descriptor. A private shallow boundary may be present or absent: absent-to-absent is a verified no-op, absent-to-present uses macOS `renameatx_np(RENAME_EXCL)` or Linux `renameat2(RENAME_NOREPLACE)`, and a receipt-bound existing source uses `RENAME_SWAP` / `RENAME_EXCHANGE`. Present-to-absent exchanges an owner-bound empty deletion marker, verifies both exchanged objects, and removes the marker and prior boundary with directory durability checks. `shallow.lock` excludes cooperative Git writers whenever mutation is needed. Only after the boundary reaches a verified, durable terminal state and the exact fetched checkout closure has passed full payload hashing does the helper descriptor-unlink and fsync the persistent fetch transaction. If that final directory fsync fails, it recreates and fsyncs a recovery fence before returning failure. A failed fetch, interrupted boundary/object verification, stale `shallow.lock`, or stale fetch transaction makes even an otherwise present commit unavailable to later helper runs; the reported recovery identity binds all visible fence/boundary states.

The helper verifies the prior object's receipt-bound identity, complete bytes, and effective access before deletion. A mismatch is atomically swapped back, while rollback, post-publication recheck, final-directory-fsync, or ownership uncertainty emits a `source-shallow-cas-v1` recovery identity containing directory, expected-state, `shallow`, and lock fingerprints/digests. A stale lock fence is retained whenever recovery ownership remains provable; a durability-unverified committed deletion is reported distinctly. Missing kernel or filesystem support and cross-device results fail closed without a plain-rename fallback. These controls prevent path replacement from redirecting the write and prevent pre-publication lost updates. They do not claim a portable linearizable defense against a malicious same-UID process that ignores `shallow.lock` and mutates entries during post-swap verification; such ambiguity fails closed and retains recoverable objects where ownership can still be established.

SSH transport—including username-less and username-qualified scp-style URLs—additionally copies the resolved executable through a bounded descriptor read into a separately owner-private `0500` snapshot, binds the exact source and snapshot object/content states, and points `core.sshCommand` only at the snapshot. It revalidates both executables while disabling user SSH config, ProxyCommand/ProxyJump, hostname canonicalization, and local commands. Replacing or rewriting the original after the last source revalidation therefore cannot select different launched bytes; the separately bound snapshot remains authoritative. Before each fetch the helper also revalidates the superproject receipt, that entry's source access, source config content/object, source shallow state, and private control gitdir. The initial complete plan validation remains the mutation gate for a no-fetch apply whose receipts do not change. If a fetch runs or a deferred checkout receipt is created, the helper performs a second complete plan validation after those state changes and before target mutation.

For a new target, the helper first creates every missing directory component relative to held no-follow directory descriptors and records each new object's exact identity, owner, group, and mode. If a later open, identity check, or final lease validation fails before Git registration, cleanup walks the receipt-bound parent chain again and conditionally removes the same empty objects in reverse order with descriptor-relative `rmdir`. A missing object is already clean; a replacement, policy drift, unreadable parent, or non-empty directory is preserved and reported through the structured `target-materialization-cleanup-v1` recovery schema with the first authoritative recovery location. Timestamp-only changes do not affect the receipt. Portable `mkdirat` and `rmdir` do not provide create-and-open or inode-conditional removal in one operation: a malicious same-UID replacement before the first post-`mkdirat` snapshot or after the final identity check but before `rmdir` remains outside the cooperative-race prevention guarantee; repeated descriptor/entry checks and the post-remove check detect other observable drift but cannot undo an object already removed in that residual interval.

The helper holds the exact final target and direct parent objects through the write. Git registers the worktree with `--no-checkout` from the held target descriptor and names that exact directory as `.`, so a raced symlink at the original final pathname cannot redirect Git's writes. Before either the managed or new-worktree branch reaches Git, one common gate captures a fresh source-gitdir lease and requires its path, identity/access fingerprint, mode, and purpose to equal the preflight source-access binding while also requiring the same fingerprint to equal the source-completeness gitdir binding. The helper revalidates that bridge after target materialization and retains the source lease through Git and any rollback. The registration child receives an explicit receipt-bound absolute source `GIT_COMMON_DIR`, which takes precedence over any `commondir` inserted after preflight and keeps registry writes in the selected source. The later content-checkout child instead receives an owner-private common gitdir containing exact descriptor-captured copies of source `config` and common `info/attributes` content or absence, a private `HEAD`, an exact private pack/index under `objects/pack`, and an explicit `GIT_OBJECT_DIRECTORY` naming only those private objects. Pack generation accepts only the verified sorted OID/type/size inventory and disables delta/object reuse, bitmaps, reverse indexes, commit graphs, multi-pack indexes, replacements, lazy fetch, and alternates. Its subprocess is deadline- and file-size-bounded without raising a stricter inherited file-size limit. The pack limit is an overflow-safe sum of Git's exact 12-byte header, every object's exact variable-length header, zlib's per-object `compressBound`, and the repository object-hash trailer; the canonical v2 index limit is calculated separately from its fanout, OID, CRC, offset, large-offset, and checksum tables. The process limit uses the larger output bound because `pack-objects` creates both files, while terminal validation applies each file's own exact bound and rejects one byte over. These calculations are pure integer arithmetic, so the configured 64 GiB logical-byte ceiling is validated without allocating the represented payload. The index bytes are retained and checksum/shape/inventory validated, while the potentially large pack is held by a no-follow descriptor and SHA-256 receipt without retaining a second in-memory copy. Repository-local excludes remain absent and sparse checkout is forced off. Source and private-view directory identities, complete per-directory inventories, control-file/index bytes, and pack identity/size/digest are all revalidated in the child, with inventories repeated after the potentially long pack digest and immediately before `exec`; a temporary same-UID rewrite of a live source `.gitattributes` object during private materialization cannot become checkout input, and a rewrite that prevents exact materialization fails before target or registry publication. A malicious same-UID write to a private pack or directory after its final relevant check but before stock Git opens that pathname remains outside the portable prevention guarantee; held descriptors, the random private root, repeated gates, and final closure validation cannot make several stock-Git path opens atomic. The view remains owned through checkout and rollback and is descriptor-safely cleaned at the terminal state. Before checkout, the helper descriptor-reads and content-binds the target's `.git` file, requires its admin directory to be one direct child of the selected source's `worktrees/`, content-binds that admin's ordinary `gitdir` backlink, and requires the backlink to resolve exactly to the current target's `.git`. This prevents two worktrees under one source from silently borrowing each other's HEAD/index. It retains the marker and backlink file descriptors plus no-follow descriptors for the source and admin entries and their direct parents until finalization ends. Immediately before `exec`, the child compares the live absolute parent paths, parent descriptors, entry names, and object descriptors against the receipt-bound identity/access-policy tuples. It invokes Git only after those checks, with explicit `--git-dir=<bound-admin> --work-tree=.` plus the private common-dir/object override, so Git does not rediscover a raced `.git` redirect or live source object byte for HEAD/index/worktree writes and a parent-observed admin/source replacement fails before Git starts.

Registration remains provisional through every final target identity, common-gitdir, HEAD, index, source access/completeness/admission, checkout-closure, and shared-prefix receipt check. Finalization opens HEAD, `commondir`, and index only relative to the retained admin descriptor, binds their exact objects/content/access policy, and revalidates those bindings together with the forward `.git` marker and admin backlink immediately before and after plan-receipt publication. Each capture and final revalidation sandwiches the pointer proof between control-file bindings and resolves `.git -> admin`, `admin gitdir -> .git`, and `commondir -> source` component by component with descriptor-relative `O_NOFOLLOW`; the endpoint fingerprint must remain the receipt-bound object, so unchanged pointer bytes cannot be redirected through an unbound intermediate symlink. Ordinary child-entry churn remains benign when the pointer endpoint property is unchanged. The same raw-index parser runs during managed preflight and its final revalidation before any checkout probe or real checkout is invoked. Finalization also retains the exact index bytes read from the admin descriptor, verifies a non-zero repository-format checksum, parses index versions 2 through 4 without consulting the live path, enforces canonical raw-byte entry order and an aggregate expanded-path bound, and rejects conflict stages plus assume-valid/extended/split/sparse/resolve-undo/fsmonitor/untracked-cache/end-of-index-entry/parallel-offset and unknown-extension state. Git writes run with skip-hash, split/sparse, untracked-cache, end-of-index-entry, and parallel index extensions disabled. A cache-tree extension is accepted only after its complete recursive directory set, entry counts, and every valid tree OID match `entry.sha`, including non-root empty target trees. Its sibling records follow Git cache-tree.c `subtree_name_cmp`/`write_one` order—component length first, then raw name bytes—which is intentionally different from canonical tree-entry name order; the full canonical stage-0 `(mode, object id, raw path)` sequence must still equal that target tree. This protected property is the immutable captured index semantics. Stat-cache fields do not change that property and are not used as file-content evidence, so this layer does not independently hash the published working-tree bytes. It never asks Git to rediscover the target's current `.git` path during that interval. Before setting `registration_attempted`, the helper opens `worktrees/` relative to the held source descriptor and takes two equal bounded scans of every raw direct child `(name bytes, device, inode, kind, owner, group, mode)`; it repeats the same descriptor-bound scan after add and after rollback. An initially missing root and a later empty root are equivalent because Git may create or remove that empty container, but any direct child addition, removal, replacement, type change, or access-policy change is uncertain. Internal HEAD/index/logs/`gitdir` churn within an unchanged pre-existing admin directory does not change this protected property. Thus a failed add whose incomplete admin record has a missing or unusable `gitdir` is retained with an exact `worktree-registration-recovery-v1` location even when `git worktree list` omits it. The after-scan `worktrees/` fingerprint must equal the control receipt's held parent fingerprint, and the only allowed child-set transition is the addition of that receipt's exact admin entry; only after this ownership proof succeeds may the normal or recovered-control path invoke Git removal. A failed proof preserves the registered target and publishes its recovery locator. A failure keeps the control receipt alive while removing the exact ownership-proven worktree through the held target-parent descriptor. Immediately before recursive `git worktree remove`, the child identity gate also compares that materialized target's retained parent/name/object descriptors with the published target entry. A replacement visible there prevents Git from starting and preserves both registration and replacement for recovery; otherwise rollback verifies registry and target absence and removes only still-matching transaction-created parent directories. The ambiguous-registration query after a failed add and the final registry-absence query after removal both execute through the still-held source lease's child identity gate, with parent-side lease validation immediately before and after the bounded query. Known rollback additionally checks the original admin descriptor, its held parent descriptor, and exact raw admin name after Git removal; only ENOENT plus a raw inventory equal to the pre-add baseline authorizes target-parent cleanup. Source identity, access-policy, registry-inventory, target-entry, or query drift preserves the remaining target/materialization state for recovery. If the forward marker or admin backlink was replaced, rollback creates the corresponding retained original bytes descriptor-relatively and atomically exchanges them with each unexpected regular-file entry so stock Git can validate and unregister the transaction-owned worktree; every unexpected entry stays under its original directory descriptor and a private temporary name and is restored if unregistering fails. Existing managed targets skip registration but retain the same control/final-state receipts across checkout, postvalidation, and publication. A recursive shared-prefix access failure never changes the mode of such a surviving managed checkout; only a newly registered parent may temporarily gain owner access needed for its enclosing worktree rollback. A malicious same-UID process that replaces a source/admin/target path in the residual interval after the child identity check but before stock Git opens that absolute path is outside this portable helper's prevention guarantee; postvalidation still detects it, but POSIX/macOS expose no directory-fd Git interface that can make that checkout/remove interval linearizable. The conceptual registration operation, with the process cwd already anchored to the held target directory, is:

```bash
git --git-dir=/path/to/source/.git/modules/third_party/libexample \
  worktree add --detach --no-checkout \
  . \
  <gitlink-sha>
```

When selected siblings have the same exact missing ancestor, such as `vendor/a` and `vendor/b`, the plan records that ancestor separately from either final worktree root. The complete preflight proves every shared ancestor absent before the first mutation. After one participant creates it descriptor-relatively and completes postvalidation, the plan publishes the created object's device, inode, kind, owner, group, and mode as a plan-owned receipt. A later participant may consume only the longest byte-exact original-component prefix covered by those receipts; it rechecks effective write/search access and filesystem name semantics, then carries the bound nodes into descriptor-relative materialization. The target-collision trie rejects different raw component spellings that share a case-folded or Unicode-normalized token before apply, so `Vendor`/`vendor` or NFC/NFD aliases never become shared receipts. Final worktree roots are not published to the sibling pool.

For recursion, a parent checkout can create a planned shared child prefix before either child target is materialized. For example, checking out the parent can create `group` while the direct child targets are `group/left` and `group/right`. Raw participant inventories include deeper descendants, but authorization maps each descendant to its nearest direct-child worktree subtree: `group/left/nested/grandchild` therefore reinforces the `group/left` owner instead of preventing `group` from being bound. A candidate prefix must remain a strict prefix of every collapsed direct-child owner; prefixes beneath `group/left` stop at that final worktree root and are left to the child transaction. The helper starts at the still-held parent-target descriptor and opens each component with no-follow directory operations, comparing the entry before and after open with the opened object and live path. Every accepted prefix binds its exact identity, owner, group, permission mode, owner `u+w/u+x` bits, and effective write/search access; requiring both mode and effective access prevents a root/DAC-override probe from authorizing an owner-read-only directory. Unrelated checkout content and final target roots are never promoted into the shared receipt pool. The helper validates the complete staged receipt set before atomically publishing it with the parent's post-validation root receipt. If descriptor binding, policy validation, or receipt publication fails after a new worktree was registered, it removes that exact worktree through the held target-parent descriptor and verifies both target absence and source-registry absence before returning the original failure. Each direct descendant must later prove its path traverses the same parent and shared-prefix objects. Rebinding a replacement directory after the parent lease closes is rejected. Replacing a shared ancestor after publication likewise fails its identity receipt; ordinary child-entry churn does not.

Important details:

- Use detached HEAD. Git does not allow the same branch checked out in multiple worktrees from one repo.
- Use the submodule name for `.git/modules/<name>` and the submodule path for the checkout location.
- Read the expected SHA from the target superproject index, not from the source checkout's current submodule working tree.
- For nested submodules, read `.gitmodules` and gitlink SHAs from the parent source repo at the target commit.
- Passing `--work-tree` is useful when a source `.git/modules/<path>` repo exists but its original `core.worktree` points at a deleted worktree.

## Failure Modes

### Missing Source Repo

The source repo for `.git/modules/<submodule-name>` must already exist. Initialize it in the source checkout first:

```bash
git -C /path/to/source-superproject submodule update --init --depth 1 -- third_party/libexample
```

If automation policy forbids cloning, stop and report the missing source repo.

### Missing Commit In A Shallow Source

The helper first checks:

```bash
git --git-dir=<source-gitdir> --work-tree=<target-path> cat-file -e <sha>^{commit}
```

If the commit is missing, the default is to stop without a network mutation and report the exact planned fetch. The helper may attempt the fetch only when the task explicitly authorizes missing-commit fetches and the invocation includes `--fetch-missing`. The displayed shape below is conceptual; the helper binds the source object directory in its frozen environment, substitutes the receipt's exact URL, and applies its closed transport options:

```bash
GIT_OBJECT_DIRECTORY=<source-gitdir>/objects git --git-dir=<private-control-gitdir> fetch --depth 1 <exact-url> <sha>
```

`--dry-run --fetch-missing` prints this action without executing it. If a missing parent commit prevents recursive `.gitmodules` inspection, both plan-only and apply runs stop before any fetch because the helper cannot prove the complete recursive target set first. Fetch that commit separately and rerun, or explicitly use `--no-recursive --fetch-missing` for the selected parent and then rerun the recursive plan once the object is local. The helper never performs a recursive preflight mutation merely to discover more targets.

Some servers reject raw SHA fetches. In that case, report the failure and request or use separately authorized branch/tag fetch semantics before rerunning:

```bash
GIT_OBJECT_DIRECTORY=<source-gitdir>/objects git --git-dir=<private-control-gitdir> fetch --depth 100 <exact-url> <branch-or-tag>
```

Do not silently unshallow; full history fetches can be much larger than the user intended.

### Existing Target Directory

Safe cases:

- Missing path.
- Empty directory with `--force-replace-empty`.
- Existing linked worktree whose `git rev-parse --git-common-dir` is exactly the intended source gitdir.

Unsafe cases:

- Non-empty directory that is not already a linked worktree for the intended source repo.
- Standard submodule checkout owned by the target superproject.
- Worktree with local changes.

Stop and report rather than deleting or overwriting.

### Ignored Or Filtered Checkout Content

An ignored untracked path that overlaps a managed target write is a preflight error even though ordinary `git status` omits it. Move or preserve that content outside the worktree and rerun; the helper will not ask Git to overwrite it.

A target-tree `filter=<driver>` attribute is also a preflight error. Install/configure the filter separately and use an ordinary repository workflow that intentionally trusts it, or remove the attribute requirement in an authorized source change. This helper never treats a missing optional filter as a safe raw checkout.

### Filesystem Name Aliases

The plan binds name comparison separately at every target's deepest existing parent directory rather than assuming the repository root describes descendant mounts or ext4 casefold directories. Existing components are keyed by device/inode identity; missing suffixes use that anchor's case and Unicode policy. A bounded trie detects aliases and ancestor overlap without a pairwise plan scan; DFS-active ancestor metadata makes each insertion linear in path depth instead of repeatedly walking logical parent links. Every anchor object and policy is revalidated before apply, so a later target's policy drift blocks the first mutation.

On macOS the probe reads the anchor volume's case capability and always uses filesystem-derived canonical Unicode comparison, even when `core.precomposeUnicode=false`. On Linux the helper opens the anchor once with no-follow directory flags, then uses that same descriptor for the actual lookup probe, directory casefold ioctl, and bounded `fstatfs` classification. A lookup proof checks the original entry before and after the alternate-case lookup; deletion, replacement, or unreadability is inconclusive and fails closed. When both exact spellings are enumerated as separate dirents, a shared inode is treated as a hardlink proof of case sensitivity rather than as a case-insensitive alias. An empty directory is accepted as case-sensitive only for a known direct-filesystem/flag combination.

Case evidence does not prove Unicode normalization behavior. Linux uses literal Unicode collision keys only for a separately allowlisted byte-exact filesystem with the directory casefold flag explicitly disabled. An unknown CIFS/FUSE/NFS-like filesystem with a valid existing-entry case lookup uses conservative NFD collision keys, which may reject extra paths but does not rewrite names on disk. An empty unknown filesystem without case evidence, XFS without a filesystem-wide ASCII-CI proof, and every OverlayFS merged directory fail closed before any fetch or target mutation; repository `core.ignoreCase` and `core.precomposeUnicode=false` are never treated as authority for literal names. Git paths containing backslashes, drive prefixes, UNC forms, absolute paths, or unsafe segments fail before target construction, and the lexical target is proved to remain under the selected root.

## Example Large Repo Pattern

This workflow is useful in large linked-worktree setups where:

- The target repo was a linked worktree.
- The source superproject's `.git/modules/<submodule-name>` tree was already populated.
- Many submodule repos were shallow.
- Several top-level submodules had nested submodules.

The reusable lesson is to use the target superproject index for desired gitlink SHAs,
use the source `.git/modules` tree for object storage, and keep the submodule checkouts detached.
